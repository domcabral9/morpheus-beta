# Changelog — Morpheus — Agosto 2026

Log narrativo, cronológico, etapa por etapa/PR por PR. Parte do arquivo dividido por mês —
ver [`../CHANGELOG.md`](../CHANGELOG.md) para o índice completo.

## 2026-08-01

- **"Perfumaria" de PR - labels e milestones (processo, sem mudança de código).** Backlog aberto em
  2026-07-31 depois que o usuário notou campos nativos do GitHub (Reviewers/Assignees/Labels/
  Milestone) vazios navegando pelas PRs mescladas. Escopo confirmado via `AskUserQuestion`:
  aplicação retroativa nas 85 PRs já mescladas, labels **e** milestones.
  - 3 labels novas criadas (`chore`, `style`, `build`), completando a taxonomia que espelha os
    prefixos de commit convencional usados no repo (`feat`→`enhancement`, `fix`→`bug`,
    `docs`→`documentation` já existiam como label padrão do GitHub). Aplicadas em todas as 85 PRs -
    nas 24 anteriores à adoção do prefixo de commit (`feat:`/`docs:`/etc., PRs #1-#24), o tipo foi
    inferido pelo conteúdo real da PR (quase todas `enhancement`, exceto a #24, puramente visual,
    marcada `style`).
  - 12 milestones criados retroativamente, um por arco de feature já entregue (ex.: "Renovação
    anual de homologação", "Avaliação de risco de fornecedores", "Política de senha (plataforma)"),
    cobrindo as 85 PRs sem sobra. Documentado em [`DEVELOPMENT.md`](./DEVELOPMENT.md#labels-e-milestones-de-pr).
  - **Gotcha real encontrado**: `gh pr edit --milestone "<nome>"` só resolve milestones **abertos**
    por título - como os 12 foram criados já `closed` (features todas concluídas), a primeira
    tentativa falhou nas 85 PRs com `'<nome>' not found`, embora as labels do mesmo comando tivessem
    sido aplicadas normalmente. Contornado usando `gh api -X PATCH repos/.../issues/:number -f
    milestone=<número>` diretamente, que aceita milestone fechado sem problema.
  - Reviewers formais ficaram de fora por decisão já registrada (projeto solo, confirmação de merge
    é verbal - ver seção de CI em `DEVELOPMENT.md`); self-assign como `assignee` já vinha sendo
    aplicado desde que o item entrou no backlog.
- **Tela de perfil / autoatendimento, Fase 1 (2026-08-01): schema + API.** Terceiro item do backlog
  "Autenticação" (aberto 2026-07-26), priorizado depois da política de senha (item 2, DONE) - ordem
  confirmada com o usuário via `AskUserQuestion`: perfil primeiro, porque o próximo item (2FA) vai
  precisar de um lugar pra morar. Escopo desta fase: nome + avatar/foto editáveis; email fica só
  leitura (é a chave de login, `@@unique([tenantId, email])`).
  - `User.avatarPath String?` (novo, chave de storage, mesmo padrão de `Tenant.logoUrl`), migration
    aditiva `add_user_avatar_path`.
  - `UsersModule` importa `StorageModule` (não é `@Global()` - mesmo que `TenantsModule` já fazia).
    `UsersRepository` ganha um `select` dedicado (`ownProfileSelect`, nunca vaza `passwordHash` cru,
    mesma disciplina do `userAdminSelect` de admin) + `findOwnProfile`/`updateName`/`setAvatarPath`.
  - `UsersService`: `getOwnProfile`/`updateOwnProfile`/`uploadOwnAvatar`/`getOwnAvatar`, espelhando
    exatamente o padrão já usado pro logo do tenant (`TenantsService.uploadLogo`/`getLogo`) e pra
    senha própria (`changeOwnPassword`) - mutações gravam `AuditLogService.record()` explícito
    (`metadata: {field: "name"|"avatar", initiatedBy: "self"}`), já que o `@Audit()` decorator não
    carrega esse metadata dependente de runtime.
  - 4 rotas novas em `AuthController` (não em `UsersController` - mesma fronteira já estabelecida
    pra `/auth/password`: `AuthController` = ações sobre a própria conta, `UsersController` = admin
    gerenciando terceiros): `GET/PATCH /auth/profile`, `POST/GET /auth/avatar` (limite 2MB, só
    PNG/JPEG, mesmo `FileInterceptor` do upload de logo). Nenhuma com `@RequirePermissions` (age só
    sobre `@CurrentUser()`, nunca aceita id de terceiro) nem `@Throttle` dedicado (não é alvo de
    força bruta).
  - **Decisão explícita, não feita nesta fase**: `avatarPath`/`hasAvatar` não entram no payload do
    JWT - o avatar só aparece na tela de perfil (Fase 2), a sidebar continua com iniciais por
    enquanto. Tocar o formato do token é escopo maior que o pedido original.
  - **Testes**: 9 casos novos em `users.service.spec.ts` (mapeamento sem vazar hash, nome
    vazio/trimado, MIME inválido sem tocar o storage, chave de avatar correta, 404 sem avatar).
    Validação manual via curl contra o `demo` seedado, incluindo checagem cross-user explícita (2
    tokens diferentes, confirmado que cada um só enxerga o próprio perfil/avatar - acaba sendo o
    primeiro pedaço da Fase 3 de segurança já verificado cedo) e rejeição de campo extra no DTO
    (`forbidNonWhitelisted`), arquivo >2MB (413) e MIME forjado (400). Dado de teste (nome/avatar do
    `admin@morpheus.demo`) revertido via SQL ao final, sem deixar rastro no ambiente demo.

- **Tela de perfil / autoatendimento, Fase 3 (2026-08-01): revisão de segurança (OWASP Top 10).**
  Pedido explícito do usuário, motivado pela preocupação com IDOR à medida que o número de endpoints
  do projeto cresce - fase nova no ritmo do projeto, não fazia parte do plano original. Duas frentes:
  - **Automatizada**: skill `/security-review` sobre o diff acumulado das Fases 1-2 (4 rotas novas em
    `AuthController`, `UsersService`, `UsersRepository`, `User.avatarPath`, rota `/profile`). Nenhuma
    vulnerabilidade de alta confiança encontrada. Verificado por leitura de código: as 4 rotas travam
    toda operação em `@CurrentUser().id` (JWT verificado), sem nenhum parâmetro de id de terceiro por
    path/query/body (A01); `ValidationPipe({whitelist, forbidNonWhitelisted, transform})` global
    (`main.ts`) rejeita campos extras no DTO em vez de ignorar silenciosamente (A03); chave de storage
    do avatar (`user-avatars/${actor.id}/avatar.${extensão}`) monta a partir só do JWT + um dicionário
    fixo de extensão, sem vetor de path traversal (A04); headers de resposta e mensagens de erro do
    `GET /auth/avatar` não vazam path interno/stack trace (A05).
  - **Manual (checklist específico das 4 rotas)**: a maior parte já tinha sido exercida ao vivo na
    própria Fase 1, não só lida no código - reconfirmado aqui, não redigido do zero: 2 tokens
    diferentes (`admin@morpheus.demo`/`usuario@morpheus.demo`) confirmando isolamento cross-user
    (A01); `PATCH /auth/profile` com campo extra não declarado (`isSuperAdmin`) rejeitado com 400
    (A03); arquivo >2MB rejeitado com 413, MIME forjado (`.gif` como `image/gif`) rejeitado com 400
    antes de qualquer gravação no storage (A04).
  - **Achado real, mas fora do escopo pra corrigir agora**: MIME-type do upload de avatar é confiado
    do client (`file.mimetype`, sem checagem de magic bytes) - mas isso **espelha exatamente** o
    padrão já em produção do upload de logo do tenant (`tenants.controller.ts`/`tenants.service.ts`),
    não é uma regressão introduzida por esta feature, e não há vetor concreto de um usuário afetar a
    sessão/dados de outro por essa via (o arquivo servido de volta só é visível ao próprio usuário,
    com `Content-Type` sempre fixado pelo servidor via extensão, nunca sniffado do conteúdo).
    Registrado como risco preexistente aceito, não bloqueia esta feature - candidato a
    hardening futuro (verificação de magic bytes) se algum dia isso deixar de ser um projeto
    educacional/portfólio solo.
  - **Nenhuma mudança de código nesta fase** - fase 100% de verificação, sem achado que justificasse
    correção.

## 2026-08-02

- **2FA (TOTP, RFC 6238), Fase 1 (2026-08-02): schema + config.** Quarto item do backlog
  "Autenticação" (1: passwordless - adiado; 2: política de senha - DONE; 3: perfil de autoatendimento
  - DONE; agora: 2FA). Escopo confirmado via `AskUserQuestion`: padrão TOTP/RFC 6238 (sem SDK de
  terceiros tipo Authy), toggle de exigência plataforma inteira (cross-tenant, mesmo padrão de
  `PlatformPasswordPolicy`), construído antes do arco de passwordless (que segue adiado, separado).
  - `User` ganha `totpSecret String?` (criptografado via `CryptoService`/AES-256-GCM, mesmo mecanismo
    já usado em `RefreshToken.ipAddress` - reversível de propósito, o servidor precisa ler o secret de
    volta a cada verificação), `totpPendingSecret String?` (secret do setup ainda não confirmado por
    um código válido - nunca promovido ao secret ativo sem essa confirmação) e
    `totpEnabled Boolean @default(false)`.
  - Novo model `TwoFactorBackupCode` (tabela própria, mesmo padrão de `RefreshToken`: lista de
    segredos vinculada a um usuário, hash individual - nunca um array cru no `User`): `codeHash`
    (bcrypt), `usedAt` (uso único, marcado por código individual).
  - Novo model singleton `PlatformTwoFactorPolicy` (`id @default("singleton")`, mesmo padrão de
    `PlatformPasswordPolicy`): campo único `enforced`. **Decisão registrada explicitamente**: nesta
    primeira entrega é um nudge, não um bloqueio de login - quando ligado, só sinaliza em
    `GET /auth/profile` (Fase 4) para quem ainda não configurou 2FA; forçar o login em si fica como
    extensão futura isolada, se pedida (decisão confirmada com o usuário via `AskUserQuestion`, ver
    plano).
  - Migration aditiva (`add_two_factor_auth`) - só `ALTER TABLE users ADD COLUMN` + 2 `CREATE TABLE`,
    sem tocar dado existente. Env vars novas (`JWT_PREAUTH_SECRET`/`JWT_PREAUTH_EXPIRES_IN`, default
    `5m`) para o token de escopo limitado que a Fase 3 vai usar entre "senha correta" e "código
    validado" - mesma validação `min(16)` já usada pelos outros secrets JWT.
  - `docs/architecture.md`: `TWO_FACTOR_BACKUP_CODE`/`PLATFORM_TWO_FACTOR_POLICY` adicionados ao
    diagrama ER "Tenancy e RBAC" (47→49 modelos), mesma nota de "cross-tenant, sem relação" já dada a
    `PLATFORM_PASSWORD_POLICY`.
  - **Nenhuma rota/lógica nova ainda** - fase 100% de schema/config, sem comportamento novo exposto.
    Login e perfil continuam idênticos a hoje até a Fase 2.
  - **Testes**: `pnpm db:migrate` limpo, migration revisada linha a linha (aditiva, sem backfill).
    `pnpm --filter @morpheus/api lint/typecheck/test/build` verdes (`auth.service.spec.ts` precisou
    dos 3 campos novos no fixture `baseUser`, mesmo ajuste já feito quando `avatarPath` entrou no
    model). `pnpm db:seed` re-executado, confirma que os defaults novos não afetam nenhum tenant/
    usuário existente.
- **2FA (TOTP, RFC 6238), Fase 2 (2026-08-02): backend, enrollment self-service.** Módulo novo
  `apps/api/src/modules/two-factor/` - gera/confirma o secret TOTP, backup codes, e as 4 rotas de
  autoatendimento em `AuthController` (`POST /auth/2fa/setup`, `POST /auth/2fa/enable`,
  `PATCH /auth/2fa/disable`, `POST /auth/2fa/backup-codes/regenerate`). **Login ainda não pede
  código** - esse gate é a Fase 3, que depende deste módulo existir primeiro.
  - **Mudança de plano registrada aqui**: a lib `otplib` (recomendação original do plano) acabou de
    publicar uma reescrita major (v13) cujos plugins padrão de cripto/Base32 são pacotes ESM-only
    (`@scure/base`, via `@otplib/plugin-base32-scure`) - o Jest/ts-jest (CommonJS) deste projeto não
    consegue transformar esses pacotes (`SyntaxError: Unexpected token 'export'`), travando toda a
    suíte de testes do módulo. Em vez de mudar a config global de `transform`/`transformIgnorePatterns`
    do Jest por causa de uma dependência isolada (mudança de risco maior, afeta a suíte inteira),
    a lib foi removida e o algoritmo (RFC 6238 sobre RFC 4226, HMAC-SHA1 + Base32 padrão RFC 4648) foi
    implementado direto com `node:crypto` em `two-factor.util.ts` (~90 linhas, sem dependência nova) -
    curto o bastante pra ser auditável de propósito, já que é justamente a peça mais sensível da
    feature. Verificado contra o vetor de teste oficial da RFC 6238 Apêndice B (secret
    `12345678901234567890`, T=59s → código `287082` truncado em 6 dígitos) nos testes unitários, não
    só "parece certo".
  - `two-factor.util.ts`: `generateTotpSecret` (160 bits, Base32), `buildOtpauthUri` (URI
    `otpauth://` padrão pro QR code), `verifyTotpCode` (±1 período/30s de tolerância de relógio,
    comparação em tempo constante via `timingSafeEqual`), `generateBackupCodes` (10 códigos
    `XXXX-XXXX`, alfabeto sem `0/O/1/I`).
  - `two-factor.repository.ts`/`.service.ts`: `beginSetup` (rejeita SSO-only e já-habilitado, grava
    `totpPendingSecret` criptografado via `CryptoService` - mesmo mecanismo de
    `RefreshToken.ipAddress`), `confirmSetup` (valida o código contra o pendente, só então promove a
    `totpSecret` + gera os 10 backup codes, hash bcrypt individual em `TwoFactorBackupCode`),
    `disable`/`regenerateBackupCodes` (exigem reautenticação com a senha atual, mesmo padrão de
    `changeOwnPassword`), `verifyLoginCode` (usado pela Fase 3: tenta TOTP, cai pra backup code não
    usado, nunca audita tentativa falha - mesmo padrão já usado em `validateLocalUser`). QR code
    gerado no servidor via `qrcode.toDataURL` (já instalado desde antes desta feature).
  - `UsersService.getOwnProfile`/`ownProfileSelect`: novo `hasTwoFactorEnabled` no payload de
    `GET /auth/profile`.
  - **Testes**: `two-factor.util.spec.ts` (secret/URI/backup codes + o vetor RFC 6238 acima) e
    `two-factor.service.spec.ts` (14 casos: SSO-only e já-habilitado rejeitados no setup, código
    errado não persiste nada, código certo comita + audita + devolve 10 códigos únicos, reautenticação
    errada em disable/regenerate, TOTP e backup code aceitos em `verifyLoginCode`, backup code marcado
    usado, nada bate → 401). Manual via curl contra `admin@morpheus.demo`: setup → QR/secret → código
    errado rejeitado (400) → código certo aceito (201, 10 backup codes) → `GET /auth/profile` reflete
    `hasTwoFactorEnabled:true` → novo setup enquanto já habilitado rejeitado (400) → campo extra
    (`isSuperAdmin`) no body de `enable` rejeitado pelo `ValidationPipe` (400) → `disable` com senha
    errada (401) → `regenerate` sem 2FA habilitado, depois de desabilitar (400) → `disable` com senha
    certa (200, `hasTwoFactorEnabled:false` de volta) → 6 tentativas rápidas de `disable` com senha
    errada confirmam o rate-limit (`429` a partir da 5ª requisição na janela de 60s, contando as
    chamadas anteriores na mesma rota). Conta demo devolvida ao estado limpo (2FA desabilitado, sem
    backup codes) ao final. `pnpm --filter @morpheus/api lint/typecheck/test/build` verdes.
