## 2026-08-01

- **"Perfumaria" de PR - labels e milestones (processo, sem mudança de código).** Backlog aberto em
  2026-07-31 depois que o usuário notou campos nativos do GitHub (Reviewers/Assignees/Labels/
  Milestone) vazios navegando pelas PRs mescladas. Escopo confirmado via `AskUserQuestion`:
  aplicação retroativa nas 85 PRs já mescladas, labels **e** milestones.
  - 3 labels novas criadas (`chore`, `style`, `build`), completando a taxonomia que espelha os
    prefixos de commit convencional usados no repo (`feat`→`enhancement`, `fix`→`bug`,
    `docs`→`documentation` já existiam como label padrão do GitHub). Aplicadas em todas as 85 PRs -
    nas 24 anteriores à adoção do prefixo de commit (`feat:`/`docs:`/etc., PRs #1-#24), o tipo foi
    inferido pelo conteúdo real da PR (quase todas `enhancement`, exceto a #24, puramente visual,
    marcada `style`).
  - 12 milestones criados retroativamente, um por arco de feature já entregue (ex.: "Renovação
    anual de homologação", "Avaliação de risco de fornecedores", "Política de senha (plataforma)"),
    cobrindo as 85 PRs sem sobra. Documentado em [`DEVELOPMENT.md`](./DEVELOPMENT.md#labels-e-milestones-de-pr).
  - **Gotcha real encontrado**: `gh pr edit --milestone "<nome>"` só resolve milestones **abertos**
    por título - como os 12 foram criados já `closed` (features todas concluídas), a primeira
    tentativa falhou nas 85 PRs com `'<nome>' not found`, embora as labels do mesmo comando tivessem
    sido aplicadas normalmente. Contornado usando `gh api -X PATCH repos/.../issues/:number -f
    milestone=<número>` diretamente, que aceita milestone fechado sem problema.
  - Reviewers formais ficaram de fora por decisão já registrada (projeto solo, confirmação de merge
    é verbal - ver seção de CI em `DEVELOPMENT.md`); self-assign como `assignee` já vinha sendo
    aplicado desde que o item entrou no backlog.

- **Tela de perfil / autoatendimento, Fase 3 (2026-08-01): revisão de segurança (OWASP Top 10).**
  Pedido explícito do usuário, motivado pela preocupação com IDOR à medida que o número de endpoints
  do projeto cresce - fase nova no ritmo do projeto, não fazia parte do plano original. Duas frentes:
  - **Automatizada**: skill `/security-review` sobre o diff acumulado das Fases 1-2 (4 rotas novas em
    `AuthController`, `UsersService`, `UsersRepository`, `User.avatarPath`, rota `/profile`). Nenhuma
    vulnerabilidade de alta confiança encontrada. Verificado por leitura de código: as 4 rotas travam
    toda operação em `@CurrentUser().id` (JWT verificado), sem nenhum parâmetro de id de terceiro por
    path/query/body (A01); `ValidationPipe({whitelist, forbidNonWhitelisted, transform})` global
    (`main.ts`) rejeita campos extras no DTO em vez de ignorar silenciosamente (A03); chave de storage
    do avatar (`user-avatars/${actor.id}/avatar.${extensão}`) monta a partir só do JWT + um dicionário
    fixo de extensão, sem vetor de path traversal (A04); headers de resposta e mensagens de erro do
    `GET /auth/avatar` não vazam path interno/stack trace (A05).
  - **Manual (checklist específico das 4 rotas)**: a maior parte já tinha sido exercida ao vivo na
    própria Fase 1, não só lida no código - reconfirmado aqui, não redigido do zero: 2 tokens
    diferentes (`admin@morpheus.demo`/`usuario@morpheus.demo`) confirmando isolamento cross-user
    (A01); `PATCH /auth/profile` com campo extra não declarado (`isSuperAdmin`) rejeitado com 400
    (A03); arquivo >2MB rejeitado com 413, MIME forjado (`.gif` como `image/gif`) rejeitado com 400
    antes de qualquer gravação no storage (A04).
  - **Achado real, mas fora do escopo pra corrigir agora**: MIME-type do upload de avatar é confiado
    do client (`file.mimetype`, sem checagem de magic bytes) - mas isso **espelha exatamente** o
    padrão já em produção do upload de logo do tenant (`tenants.controller.ts`/`tenants.service.ts`),
    não é uma regressão introduzida por esta feature, e não há vetor concreto de um usuário afetar a
    sessão/dados de outro por essa via (o arquivo servido de volta só é visível ao próprio usuário,
    com `Content-Type` sempre fixado pelo servidor via extensão, nunca sniffado do conteúdo).
    Registrado como risco preexistente aceito, não bloqueia esta feature - candidato a
    hardening futuro (verificação de magic bytes) se algum dia isso deixar de ser um projeto
    educacional/portfólio solo.
  - **Nenhuma mudança de código nesta fase** - fase 100% de verificação, sem achado que justificasse
    correção.

- **2FA (TOTP, RFC 6238), Fase 2 (2026-08-02): backend, enrollment self-service.** Módulo novo
  `apps/api/src/modules/two-factor/` - gera/confirma o secret TOTP, backup codes, e as 4 rotas de
  autoatendimento em `AuthController` (`POST /auth/2fa/setup`, `POST /auth/2fa/enable`,
  `PATCH /auth/2fa/disable`, `POST /auth/2fa/backup-codes/regenerate`). **Login ainda não pede
  código** - esse gate é a Fase 3, que depende deste módulo existir primeiro.
  - **Mudança de plano registrada aqui**: a lib `otplib` (recomendação original do plano) acabou de

    consegue transformar esses pacotes (`SyntaxError: Unexpected token 'export'`), travando toda a
    suíte de testes do módulo. Em vez de mudar a config global de `transform`/`transformIgnorePatterns`
    do Jest por causa de uma dependência isolada (mudança de risco maior, afeta a suíte inteira),
    a lib foi removida e o algoritmo (RFC 6238 sobre RFC 4226, HMAC-SHA1 + Base32 padrão RFC 4648) foi
    implementado direto com `node:crypto` em `two-factor.util.ts` (~90 linhas, sem dependência nova) -
    curto o bastante pra ser auditável de propósito, já que é justamente a peça mais sensível da
    feature. Verificado contra o vetor de teste oficial da RFC 6238 Apêndice B (secret
    `12345678901234567890`, T=59s → código `287082` truncado em 6 dígitos) nos testes unitários, não
    só "parece certo".

    comparação em tempo constante via `timingSafeEqual`), `generateBackupCodes` (10 códigos

    `changeOwnPassword`), `verifyLoginCode` (usado pela Fase 3: tenta TOTP, cai pra backup code não

  - `UsersService.getOwnProfile`/`ownProfileSelect`: novo `hasTwoFactorEnabled` no payload de

  - **Testes**: `two-factor.util.spec.ts` (secret/URI/backup codes + o vetor RFC 6238 acima) e

    errado não persiste nada, código certo comita + audita + devolve 10 códigos únicos, reautenticação

- **2FA (TOTP, RFC 6238), Fase 3 (2026-08-02): pre-auth token + gate no login.** Liga o 2FA de
  verdade no fluxo de login local - até aqui (Fases 1-2) o enrollment existia mas nada o consumia.

    `{twoFactorRequired:true, preAuthToken, expiresIn}` **sem setar nenhum cookie** (nenhuma sessão
    foi aberta); senão, segue idêntico a hoje (`{twoFactorRequired:false, accessToken, expiresIn}`).
    `AccessTokenResponseDto.twoFactorRequired` é opcional (`?: false`) - `/auth/refresh` e
    `/auth/switch-tenant` continuam devolvendo o shape de sempre, sem precisar mudar código ali (a
    ausência do campo já significa "não").
  - Novo `POST /auth/2fa/verify-login` (`@Public()`, `@Throttle(5/60s)`, guardado por `PreAuthGuard` -
    não pelo `JwtAuthGuard` global): releitura fresca do usuário (`usersService.findById`, mesmo
    padrão de `AuthService.refresh()`), `TwoFactorService.verifyLoginCode` (TOTP ou backup code), e só

    `issueTokenPair` + audit `LOGIN`), cookies setados igual a um login normal.
  - `samlCallback` ganhou um comentário explícito documentando por que não tem gate de 2FA (TOTP é
    só sobre login local; usuário SSO-only nunca tem `totpEnabled=true`, já bloqueado no `setup` da
    Fase 2) - registrado pra não parecer omissão acidental numa futura revisão.
  - **Testes**: `auth.service.spec.ts` ganhou `describe("issuePreAuthChallenge")` (assina com o
    secret certo sem tocar banco/auditoria; o token não verifica contra `JWT_ACCESS_SECRET`). Sem
    spec de controller (convenção já estabelecida no projeto - nenhum `*.controller.spec.ts` existe
    em lugar nenhum da API; a fiação do controller é validada via curl manual, como sempre). Manual
    via curl, fluxo completo contra `admin@morpheus.demo`: login sem 2FA idêntico a hoje (baseline,
    sem regressão) → habilita 2FA → login com 2FA devolve o desafio sem `Set-Cookie` → `verify-login`
    com código errado (401) → com o access token normal no lugar do pre-auth token (401, secret
    diferente) → o pre-auth token usado como Bearer normal em `GET /auth/me` (401, mesma razão ao
    contrário) → código certo (200, `Set-Cookie` de refresh+CSRF, sessão completa) → rate-limit
    confirmado (429) → `disable` restaura o estado limpo da conta ao final. **Observação registrada,

    um login por senha normal (nada impede logar duas vezes com a mesma senha); revisar de novo na
    Fase 7 (segurança) se isso merece virar single-use.

## 2026-08-12 (continuação): TypeScript 7, achado mais profundo, não é só um plugin desatualizado

A pedido do usuário, investigação adicional sobre o bloqueio do `#70` (por que o `typescript-eslint`
recusa TS 7.0) foi além de ler o guard de código. Checou a fonte que a própria mensagem de erro aponta
(o devblog da Microsoft sobre TS 7.0) e a issue de rastreamento `typescript-eslint#10940`. Achado muda
o quadro de forma real:

1. **TypeScript 7.0 não expõe uma API JS programável de verdade nesta versão**, é a reescrita nativa
   em Go (`tsgo`). A própria Microsoft publicou um pacote-ponte, `@typescript/typescript6` (confirmado
   real no npm, v6.0.2), e orienta ferramentas a fazerem alias de `"typescript"` pra esse pacote
   durante a transição, não pro `typescript@7.0.2` literal. Ou seja, o próprio caminho que o PR `#70`
   propõe (bump direto de `typescript` pra `^7.0.2`) é o que a Microsoft recomenda não seguir ainda.
2. **A issue `typescript-eslint#10940` não é "sem tempo de atualizar"**, é um problema arquitetural
   que os próprios mantenedores admitem: o ESLint não suporta parsers assíncronos, e o `tsgo`
   provavelmente só é consumível via binding nativo/WASM (assíncrono por natureza), exigindo trabalho
   de design pra levar AST e informação de tipo do mundo Go/WASM de volta pro mundo JS. Estimativa
   deles: meses, não uma versão de patch.
3. **Experimento de contornar o guard via `pnpm patch` foi cancelado antes de executar**, com base
   nesse achado, já que não é mais uma questão de "ver se o resultado do lint fica incoerente". É
   provável que o `typescript@7.0.2` nem exponha a API que o `typescript-eslint` precisa chamar como
   biblioteca, então o resultado mais provável seria um crash diferente, não dado útil novo.

**Prazo definido para reavaliar** (não ficar indefinidamente aberto sem checagem): gatilho por evento
(preferido) quando a issue `typescript-eslint#10940` fechar ou ganhar marco explícito de suporte a
TS7/`tsgo`, ou quando o TypeScript 7.1 lançar (é lá que a API nova prometida pela Microsoft realmente
aparece). Prazo de calendário como rede de segurança: **2026-11-12** (90 dias a partir de hoje).
