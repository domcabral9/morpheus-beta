# Changelog - Morpheus - Setembro 2026

Log narrativo, cronológico, etapa por etapa/PR por PR. Parte do arquivo dividido por mês -

## 2026-09-17

- **Retomada após ~3 semanas sem sessão - Dependabot havia acumulado 35 alertas abertos, 2 deles
  críticos.** Tratados imediatamente fora da janela semanal (exceção já documentada em
  `docs/security.md` pra achado crítico/ativamente explorado), depois organizada uma janela normal de
  triagem pro restante no mesmo dia. Log técnico completo, com o raciocínio de cada decisão, em
  `morpheus-ops/reports/vulnerability-log.md` (entradas de 2026-09-17) - resumo por PR abaixo.
  - **PR #215 - `next` 16.3.0 -> 16.3.3 (2 alertas críticos).** GHSA-2xp9-vwfh-vxw4 (RCE não
    autenticado via Image Optimization/AVIF) e GHSA-p293-qw3h-jr36/CVE-2026-75604 (RCE não autenticado
    em servidores Windows) - ambos no runtime de produção em si, alcançáveis sem autenticação. PR do
    próprio Dependabot já trazia o fix completo; `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` transitório
    resolvido com um re-run (gotcha já conhecido, nenhuma mudança de código). Duas PRs redundantes do
    Dependabot fechadas com comentário explicativo.
  - **PR #222 - `nodemailer` 9.0.3 -> 10.0.1.** Bump de manutenção sem alerta crítico associado;
    confirmado que `createTransport`/`.sendMail` (única superfície usada em
    `smtp-email.adapter.ts`) segue estável na v10 - a única mudança real é exigir Node >=20, já
    satisfeito.
  - **PR #224 - `@xmldom/xmldom` < 0.8.15, 10 alertas (#43, #52-#60).** Cluster de injeção (bypass de
    `requireWellFormed` via `EntityReference`/atributo/elemento/`DocType`/`ProcessingInstruction`
    malformados) e complexidade quadrática - sensível por ser parte da stack de SAML
    (`@node-saml/node-saml` -> `xml-crypto`/`xml-encryption`). Sem manifesto próprio pro Dependabot
    propor PR (transitiva); corrigido via override em `pnpm-workspace.yaml`
    (`"@xmldom/xmldom@0.8": ^0.8.15`), mesmo padrão já usado pro `deepmerge-ts` (2026-08-25).
  - **PR #226 - `multer` 2.2.0 -> 2.4.0 e `qs` 6.15.3 -> 6.16.0 (6 alertas: #49, #64-#66, #44, #50).**
    Os únicos 2 pacotes desta janela genuinamente alcançáveis em produção (`multer` via
    `@nestjs/platform-express`/`FileInterceptor`, usado em upload de avatar/logo/anexo; `qs` via
    `body-parser`/`express`, parser de toda requisição da API). `multer` pinado exato `2.2.0` (sem
    caret) pelo `@nestjs/platform-express` - override força o bump, mesmo footprint de
    dependências/engine confirmado via `npm view`.
  - **PR #228 - `mysql2`, `fast-uri`, `browserslist`, `js-yaml` (8 alertas restantes: #39, #42,
    #40/#41/#45/#46, #47/#48, #72/#73).** Todos os 4 confirmados **inertes** por rastreamento de
    dependência via `pnpm why` - presentes em `node_modules` mas sem caminho de execução real:
    `mysql2` é transitiva do `prisma` CLI (devDependency, projeto é só Postgres); `fast-uri` via `ajv`
    chega também por `@hookform/resolvers` mas nenhum resolver `ajv` é importado (projeto usa só
    `zodResolver`); `browserslist` só aparece em toolchain de build (babel/jest, `styled-jsx` do
    `next` - transformação de build, nunca executada em runtime); `js-yaml` só em `nyc`/`cosmiconfig`
    (dev), a versão de produção (`5.2.3`) já estava segura. Overrides de `js-yaml@3`/`@4`/`fast-uri@3`
    já existentes ficaram desatualizados frente a alertas novos sobre os mesmos pacotes - elevados
    junto com os 2 novos.
  - **Resultado**: 0 alertas abertos no repositório ao final do dia. Único item deliberadamente
    deferido: bundle de 6 PRs do ecossistema NestJS (`#217-#221, #223`, todos maior 11->12) - sem
    alerta de segurança associado (bump de manutenção, não vulnerabilidade), reservado pra sessão
    dedicada com investigação de peer dependencies e teste combinado.
  - Validado em cada PR: `pnpm why <pacote>` confirmando resolução única na versão corrigida,
    `pnpm --filter @morpheus/api typecheck/lint/test/build` (592 testes) ou
    `pnpm turbo run typecheck lint test build` quando o pacote também tocava `apps/web`.

## 2026-09-26

- **PR #229 - grupo minor-and-patch, 39 atualizações de rotina.** Sem alerta de segurança associado.
  Validado via checkout local: `pnpm turbo run typecheck lint test build` (8/8 tasks, 592 testes),
  sem alteração de código necessária.
- **Correção: enumeração de tenant via mensagem de erro em `POST /auth/login` (achado 2026-09-11,
  OWASP A07:2021, CWE-203 - Observable Discrepancy).** Achado durante um engajamento de teste de
  segurança real conduzido com o prompt do projeto `empires-erased` contra o próprio ambiente de
  desenvolvimento (graybox, sem autenticação, janela de 59min) - documentado como card no backlog
  (Trello) até ser escopado nesta sessão.
  - **Problema**: `POST /auth/login` devolvia `"Organização não encontrada."` pra `tenantSlug`
    inexistente, mas `"Credenciais inválidas."` (mensagem genérica) pra email inexistente/senha
    errada dentro de um tenant válido - a mensagem distinta funcionava como oráculo confiável de
    existência de tenant, sem precisar de nenhuma credencial. O próprio projeto já resolvia esse
    mesmo tipo de problema corretamente em `POST /auth/passwordless/request` (sempre `{sent:true}`
    200, independente de tenant/email existirem) - a inconsistência era só no login clássico.
  - **Correção**: novo `AuthService.validateLocalLogin(tenantSlug, email, password)` - resolve o
    tenant e valida a credencial numa única chamada, sempre com a mesma exceção genérica
    (`"Credenciais inválidas."`) nos 3 casos. `LocalStrategy.validate()` passa a chamar esse método
    único em vez de `resolveTenantIdBySlug` + `validateLocalUser` separados.
    `resolveTenantIdBySlug` continua existindo tal como estava, sem alteração - ainda usado pelo
    fluxo SAML, que tem contexto/risco diferente e não fazia parte deste achado.
  - Validado: novo teste em `auth.service.spec.ts` provando que as 3 causas de falha (tenant
    inexistente, email inexistente, senha errada) lançam a mesma `UnauthorizedException` com a mesma
    mensagem; `pnpm --filter @morpheus/api lint/typecheck/test/build` verdes (594 testes). Confirmado
    também via ambiente real (`docker compose up` + `pnpm dev` + `curl` direto contra os 3 casos): as
    3 respostas são byte-idênticas (`{"message":"Credenciais inválidas.","error":"Unauthorized",
    "statusCode":401}`), login com credencial correta continua funcionando normalmente.
