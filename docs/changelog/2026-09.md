# Changelog - Morpheus - Setembro 2026

Log narrativo, cronológico, etapa por etapa/PR por PR. Parte do arquivo dividido por mês -
ver [`../CHANGELOG.md`](../CHANGELOG.md) para o índice completo.

## 2026-09-17

- **Retomada após ~3 semanas sem sessão - Dependabot havia acumulado 35 alertas abertos, 2 deles
  críticos.** Tratados imediatamente fora da janela semanal (exceção já documentada em
  `docs/security.md` pra achado crítico/ativamente explorado), depois organizada uma janela normal de
  triagem pro restante no mesmo dia. Log técnico completo, com o raciocínio de cada decisão, em
  `morpheus-ops/reports/vulnerability-log.md` (entradas de 2026-09-17) - resumo por PR abaixo.
  - **PR #215 - `next` 16.3.0 -> 16.3.3 (2 alertas críticos).** GHSA-2xp9-vwfh-vxw4 (RCE não
    autenticado via Image Optimization/AVIF) e GHSA-p293-qw3h-jr36/CVE-2026-75604 (RCE não autenticado
    em servidores Windows) - ambos no runtime de produção em si, alcançáveis sem autenticação. PR do
    próprio Dependabot já trazia o fix completo; `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION` transitório
    resolvido com um re-run (gotcha já conhecido, nenhuma mudança de código). Duas PRs redundantes do
    Dependabot fechadas com comentário explicativo.
  - **PR #222 - `nodemailer` 9.0.3 -> 10.0.1.** Bump de manutenção sem alerta crítico associado;
    confirmado que `createTransport`/`.sendMail` (única superfície usada em
    `smtp-email.adapter.ts`) segue estável na v10 - a única mudança real é exigir Node >=20, já
    satisfeito.
  - **PR #224 - `@xmldom/xmldom` < 0.8.15, 10 alertas (#43, #52-#60).** Cluster de injeção (bypass de
    `requireWellFormed` via `EntityReference`/atributo/elemento/`DocType`/`ProcessingInstruction`
    malformados) e complexidade quadrática - sensível por ser parte da stack de SAML
    (`@node-saml/node-saml` -> `xml-crypto`/`xml-encryption`). Sem manifesto próprio pro Dependabot
    propor PR (transitiva); corrigido via override em `pnpm-workspace.yaml`
    (`"@xmldom/xmldom@0.8": ^0.8.15`), mesmo padrão já usado pro `deepmerge-ts` (2026-08-25).
  - **PR #226 - `multer` 2.2.0 -> 2.4.0 e `qs` 6.15.3 -> 6.16.0 (6 alertas: #49, #64-#66, #44, #50).**
    Os únicos 2 pacotes desta janela genuinamente alcançáveis em produção (`multer` via
    `@nestjs/platform-express`/`FileInterceptor`, usado em upload de avatar/logo/anexo; `qs` via
    `body-parser`/`express`, parser de toda requisição da API). `multer` pinado exato `2.2.0` (sem
    caret) pelo `@nestjs/platform-express` - override força o bump, mesmo footprint de
    dependências/engine confirmado via `npm view`.
  - **PR #228 - `mysql2`, `fast-uri`, `browserslist`, `js-yaml` (8 alertas restantes: #39, #42,
    #40/#41/#45/#46, #47/#48, #72/#73).** Todos os 4 confirmados **inertes** por rastreamento de
    dependência via `pnpm why` - presentes em `node_modules` mas sem caminho de execução real:
    `mysql2` é transitiva do `prisma` CLI (devDependency, projeto é só Postgres); `fast-uri` via `ajv`
    chega também por `@hookform/resolvers` mas nenhum resolver `ajv` é importado (projeto usa só
    `zodResolver`); `browserslist` só aparece em toolchain de build (babel/jest, `styled-jsx` do
    `next` - transformação de build, nunca executada em runtime); `js-yaml` só em `nyc`/`cosmiconfig`
    (dev), a versão de produção (`5.2.3`) já estava segura. Overrides de `js-yaml@3`/`@4`/`fast-uri@3`
    já existentes ficaram desatualizados frente a alertas novos sobre os mesmos pacotes - elevados
    junto com os 2 novos.
  - **Resultado**: 0 alertas abertos no repositório ao final do dia. Único item deliberadamente
    deferido: bundle de 6 PRs do ecossistema NestJS (`#217-#221, #223`, todos maior 11->12) - sem
    alerta de segurança associado (bump de manutenção, não vulnerabilidade), reservado pra sessão
    dedicada com investigação de peer dependencies e teste combinado.
  - Validado em cada PR: `pnpm why <pacote>` confirmando resolução única na versão corrigida,
    `pnpm --filter @morpheus/api typecheck/lint/test/build` (592 testes) ou
    `pnpm turbo run typecheck lint test build` quando o pacote também tocava `apps/web`.

## 2026-09-26

- **PR #229 - grupo minor-and-patch, 39 atualizações de rotina.** Sem alerta de segurança associado.
  Validado via checkout local: `pnpm turbo run typecheck lint test build` (8/8 tasks, 592 testes),
  sem alteração de código necessária.
- **Correção: enumeração de tenant via mensagem de erro em `POST /auth/login` (achado 2026-09-11,
  OWASP A07:2021, CWE-203 - Observable Discrepancy).** Achado durante um engajamento de teste de
  segurança real conduzido com o prompt do projeto `empires-erased` contra o próprio ambiente de
  desenvolvimento (graybox, sem autenticação, janela de 59min) - documentado como card no backlog
  (Trello) até ser escopado nesta sessão.
  - **Problema**: `POST /auth/login` devolvia `"Organização não encontrada."` pra `tenantSlug`
    inexistente, mas `"Credenciais inválidas."` (mensagem genérica) pra email inexistente/senha
    errada dentro de um tenant válido - a mensagem distinta funcionava como oráculo confiável de
    existência de tenant, sem precisar de nenhuma credencial. O próprio projeto já resolvia esse
    mesmo tipo de problema corretamente em `POST /auth/passwordless/request` (sempre `{sent:true}`
    200, independente de tenant/email existirem) - a inconsistência era só no login clássico.
  - **Correção**: novo `AuthService.validateLocalLogin(tenantSlug, email, password)` - resolve o
    tenant e valida a credencial numa única chamada, sempre com a mesma exceção genérica
    (`"Credenciais inválidas."`) nos 3 casos. `LocalStrategy.validate()` passa a chamar esse método
    único em vez de `resolveTenantIdBySlug` + `validateLocalUser` separados.
    `resolveTenantIdBySlug` continua existindo tal como estava, sem alteração - ainda usado pelo
    fluxo SAML, que tem contexto/risco diferente e não fazia parte deste achado.
  - Validado: novo teste em `auth.service.spec.ts` provando que as 3 causas de falha (tenant
    inexistente, email inexistente, senha errada) lançam a mesma `UnauthorizedException` com a mesma
    mensagem; `pnpm --filter @morpheus/api lint/typecheck/test/build` verdes (594 testes). Confirmado
    também via ambiente real (`docker compose up` + `pnpm dev` + `curl` direto contra os 3 casos): as
    3 respostas são byte-idênticas (`{"message":"Credenciais inválidas.","error":"Unauthorized",
    "statusCode":401}`), login com credencial correta continua funcionando normalmente.
- **Migração NestJS 11 -> 12 em `apps/api`, dedicada e cautelosa a pedido do usuário.** As 6 PRs do
  Dependabot abertas há 15 dias (`@nestjs/schematics` #217, `nestjs-pino` #218,
  `@nestjs/platform-express` #219, `@nestjs/jwt` #220, `@nestjs/terminus` #221, `@nestjs/cli` #223)
  não podiam ser mescladas isoladas - `@nestjs/platform-express@12` exige `@nestjs/core`/
  `@nestjs/common` `^12.0.0` sem fallback pra 11.x, e nenhum dos dois tinha PR própria.
  - **Rastreamento completo do encadeamento** (`npm view <pkg> peerDependencies` contra cada versão
    hoje instalada) revelou 13 pacotes precisando subir juntos na mesma instalação, não só os 6 da
    Dependabot: `@nestjs/core` 11.1.28->12.0.3, `@nestjs/common` 11.1.28->12.0.3, `@nestjs/testing`
    11.1.28->12.0.3, `@nestjs/swagger` 11.4.6->12.0.1, `@nestjs/config` 4.0.4->12.0.0 (salto de
    número grande, mas confirmado via changelog oficial do pacote: não existem versões 5.x-11.x, é
    realinhamento pra bater com a numeração do `@nestjs/core`, não 8 majors de mudança acumulada),
    `@nestjs/passport` 11.0.5->12.0.0, `@nestjs/schedule` 6.1.3->12.0.2,
    `@willsoto/nestjs-prometheus` já estava em 6.1.1 (trazido pela PR #229) - mais os 6 pacotes da
    Dependabot. `@nestjs/throttler` não precisou de bump (já aceitava core/common até `^12.0.0`).
  - **Único código que precisou mudar de verdade**: `apps/api/src/health/prisma.health.ts` usava a
    API antiga do Terminus (`HealthIndicator`/`HealthCheckError`/`getStatus`, removida na v12) -
    reescrito pro padrão novo (`HealthIndicatorService` injetado, `indicator.up()`/`.down()`, sem
    lançar exceção), preservando o mesmo formato de detalhe de falha (`{message}`).
    `health.controller.ts`/`health.controller.spec.ts` não precisaram de nenhuma alteração.
  - **Achado de infraestrutura de teste, fora do previsto no plano inicial - e que só apareceu no
    CI, não localmente.** Os pacotes core da v12 são ESM-only - o `require()` do CommonJS compilado
    pelo `ts-jest` não conseguia carregar `@nestjs/testing` direto. Corrigido localmente com
    `cross-env NODE_OPTIONS=--experimental-vm-modules` nos scripts `test`/`test:e2e` (novo
    devDependency `cross-env`, pra funcionar igual no PowerShell/cmd do Windows e no shell do CI) -
    validado limpo em Node 24.18 local, PR aberta e CI **falhou** com o mesmo erro, mesmo com o fix.
  - **Investigação da causa raiz (lida direto do código-fonte do `jest-runtime` instalado, não só
    documentação)**: o mecanismo síncrono que faz `require()` de ESM funcionar
    (`_nodeCapabilities.supportsSyncEvaluate`, em `node_modules/jest-runtime/build/index.js`) checa a
    presença de `vm.SourceTextModule.prototype.hasAsyncGraph` - uma API que só existe a partir do
    Node **24.9**, e mesmo assim só fica exposta com `--experimental-vm-modules` ativo. CI fixava
    Node `"22"` (comentário do workflow já desatualizado - dizia bater com a imagem de produção,
    mas `apps/api/Dockerfile`/`apps/web/Dockerfile` já usam `node:26-alpine` desde 2026-07-28,
    ver `docs/DEVELOPMENT.md`). Confirmado via `docker run node:22-alpine`/`node:24-alpine`/
    `node:26-alpine` com a flag: a API só aparece a partir do Node 24 - **no Node 22 é impossível,
    flag ou não**, não é uma questão de configuração do Jest. Chegou a ser tentada uma alternativa
    sem depender de nenhum recurso nativo de interop (transformar os pacotes ESM via `babel-jest` +
    `transformIgnorePatterns`) - abandonada depois de confirmar, lendo o mesmo código-fonte, que o
    `require()` de um pacote com `"type":"module"` no `package.json` cai num branch do jest-runtime
    que lança o erro direto quando `supportsSyncEvaluate` é falso, sem sequer consultar
    `transform`/`transformIgnorePatterns` - não existe contorno por config de transform pra esse caso
    específico.
  - **Correção real**: elevar o Node do CI (`.github/workflows/ci.yml`) de `"22"` pra `"26"`,
    alinhando com o que a produção já roda (e corrigindo o comentário desatualizado do workflow).
    Isso trouxe de volta o mesmo gotcha já documentado nos Dockerfiles - a partir do Node 26 o
    `corepack` não vem mais embutido na imagem (`corepack enable` falha com `corepack: not found`) -
    corrigido com o mesmo `npm install -g corepack@latest && corepack enable` já usado lá. `engines
    .node` do monorepo (`package.json` raiz) elevado de `>=20.0.0` pra `>=24.9.0`, refletindo o piso
    real agora exigido pelo teste do `apps/api`.
  - **Validado antes de reabrir a PR**: simulação completa do CI real via `docker run node:26-alpine`
    (instalação limpa com `pnpm install --frozen-lockfile` num volume Linux isolado, replicando
    exatamente os passos do workflow) - `pnpm turbo run typecheck lint test build` verde, 8/8 tasks,
    594/594 testes, incluindo `health.controller.spec.ts` com o interop ESM funcionando de verdade
    (só o aviso esperado `ExperimentalWarning: VM Modules`). Só afeta test/CI - o runtime de produção
    (`node dist/main.js`) já funcionava nativamente sem flag nenhuma mesmo antes desta correção
    (confirmado na validação da Fase 3, já rodando em Node 26 via Docker).
  - **Investigação prévia confirmou zero exposição** (grep exaustivo + 1 agente `Explore` dedicado)
    a outras mudanças de quebra da v12: nenhum uso de `@Optional()`, `ClassSerializerInterceptor`,
    Joi (via `@nestjs/config`), NATS/Kafka/`@nestjs/microservices`/GraphQL; único implementador de
    lifecycle hook no projeto inteiro é `PrismaService` (sem dependência de ordem entre providers);
    as 4 estratégias Passport existentes estendem o mixin da lib diretamente, sem herança entre si;
    todos os 55 arquivos `*.spec.ts` usam só a API básica de `Test.createTestingModule`.
  - **Validado além do ritmo padrão do projeto**, dado o risco (módulos adjacentes a autenticação +
    endpoint público de health-check): `pnpm turbo run typecheck lint test build` (8/8 tasks, 594
    testes) + validação contra o **build compilado rodando de verdade**
    (`pnpm --filter @morpheus/api build && node dist/main.js`, não só `nest start --watch`) com
    Postgres real via `docker compose up` - `GET /health/live`/`GET /health/ready` com banco no ar
    (200, `status:"ok"`) e com o container do Postgres parado de propósito (`docker stop`, confirma
    `status:"error"`/503 com o `HealthIndicatorService` novo, não regrediu pra "saudável" por
    engano); login real + rota autenticada (`GET /auth/profile`) + 401 sem token; `PATCH
    /auth/profile` com payload inválido/campo não permitido confirmando `ValidationPipe`+
    `forbidNonWhitelisted` intactos (400 estruturado, não 500 cru); `ThrottlerGuard` confirmado
    ainda bloqueando (429) após tentativas repetidas de login. `/security-review` sobre o diff
    acumulado sem achado (revisão verificou inclusive contra o código-fonte instalado do Terminus
    que a agregação up/down do health check continua correta, não "engole" falha como saudável por
    engano).
  - Fechadas as 6 PRs do Dependabot (#217-#221, #223) com comentário apontando pra esta PR
    consolidada, que já inclui o bump de cada uma.
